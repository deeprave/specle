# Requirements: add release skill

## Introduction

Specle has package version and manifest tooling but no repository-local workflow that prepares a release consistently. Publishing a release changes package metadata, records the exact managed-blueprint inventory, and deliberately includes the whole working tree in the release commit. Those are project-specific release responsibilities, not portable Specle workflow behaviour.

## Glossary

- **Release skill:** this repository's local `.agents/skills/release/SKILL.md` workflow, not a Specle-managed or distributed skill.
- **Current version:** the version declared in `pyproject.toml`.
- **Release version:** the user-provided or elicited version to be recorded for the release.
- **Release manifest:** the append-only blueprint checksum inventory generated by `specle manifest` for the release version.
- **Open pull request:** a non-draft or draft pull request that GitHub reports as open for this repository.

## Requirements

### Requirement 1: Provide a repository-local release skill

**User Story:** As a maintainer, I want a dedicated release workflow for this repository, so package-release preparation follows the repository's actual release rules.

#### Acceptance Criteria

1. The change SHALL add `.agents/skills/release/SKILL.md` as a repository-local skill.
2. The skill SHALL NOT be added to `src/specle/blueprints/`, the managed `.agents` inventory, the packaged skill index, or the release manifest.
3. The skill SHALL state that it prepares a release commit only; publishing, tags, GitHub releases, and PyPI upload remain outside its scope unless separately introduced.

### Requirement 2: Guard release preparation

**User Story:** As a maintainer, I want release preparation to stop when normal delivery work remains open, so a release cannot silently include unfinished work.

#### Acceptance Criteria

1. Before editing files or creating a branch, the skill SHALL verify that no local change is selected in `.specle/current-change`. Defined or otherwise unselected queued changes do not block a release.
2. Before editing files or creating a branch, the skill SHALL query GitHub and verify that the repository has no open pull requests.
3. If either guard fails, the skill SHALL report the blocking change or pull request and stop without modifying the working tree, Git state, version, or manifest.

### Requirement 3: Select and validate a release version

**User Story:** As a maintainer, I want to supply a release version or be asked for one, so release intent is explicit.

#### Acceptance Criteria

1. The skill SHALL use a version explicitly supplied by the user; otherwise it SHALL request one before making changes.
2. The skill SHALL read the current version from the checked-out `pyproject.toml`, which is the sole authority for release versions, and validate the proposed version using PEP 440 semantics.
3. The skill SHALL normalise the accepted proposed version to its canonical PEP 440 form and use that exact form for every later release operation, including `pyproject.toml`, branch naming, manifest generation and verification, and commit title.
4. The skill SHALL reject a canonical version that the manifest format cannot represent before creating a branch or changing files.
5. The skill SHALL proceed only when the canonical proposed version is greater than the current version; otherwise it SHALL explain the comparison and stop without making changes.

### Requirement 4: Prepare the release record

**User Story:** As a maintainer, I want the package version and managed-blueprint provenance updated together, so the release is reproducible.

#### Acceptance Criteria

1. The skill SHALL fetch and synchronise the configured delivery branch with its upstream before creating a release branch. If synchronisation cannot complete cleanly, it SHALL stop without preparing a release.
2. The skill SHALL create a branch named `chore/release_<canonical-version>` from that synchronised delivery branch after all read-only guards pass and before editing release files.
3. The skill SHALL update the version in `pyproject.toml` to the canonical release version.
4. The skill SHALL run the package's manifest command using that version to append the current complete blueprint inventory and checksums to the repository manifest, and SHALL confirm that the reported version is the same canonical value.
5. The skill SHALL stage and commit all currently unstaged and staged tracked changes and all untracked non-ignored files as one release commit; it SHALL not classify or exclude changes as unrelated.
6. Before the commit, the skill SHALL show the full proposed commit contents and request explicit user authorisation for the commit.

## Non-Functional Requirements

- This is an independent change. It relies only on already-delivered package version and manifest functionality.
- The local skill must follow the repository's delivery, security, and Markdown conventions.
- The skill must not create a pull request, push, publish, tag, or create a release as part of this change.
