# Allow sidecar activation

`activate <name>` currently starts normal changes and spikes but rejects bugfixes and refactors, whose prepared work uses separate kind-specific execution commands. Make activation a common, kind-aware entry point: retain normal change and spike selection behaviour, and route named bugfixes and refactors through any missing abbreviated preparation into `build <name>` without changing `.specle/current-change`.

Extend named build execution to abbreviated work while retaining bugfix reproduction and regression expectations, refactor behavioural invariants and baseline, lifecycle progress, verification, and delivery safeguards. Concurrent activation creates reciprocal parent/sidecar relationships. Reconcile lifecycle policy, skill instructions and metadata, installed and packaged copies, entrypoint documentation, and next-action reporting. An already selected defined spike may validly report and run `activate`, which invokes its spike workflow.

Register multiple actively commenced sidecars in a Git-ignored worktree-local registry, suggested as `.specle/current-sidecars`, without changing the normal selection or treating registry membership as durable status or a delivery relationship. Define the full sidecar lifecycle and registry ownership, inspection, cleanup, and recovery, including stale entries and worktree isolation.

When a normal change and a sidecar become active in the same worktree, in either order, link them automatically through a recoverable reciprocal update. Do not audit the user's chosen code or automatically stash or move work. Completion retains relationships for items completed together and unlinks a separately completed item from any surviving active sibling. Completion triggers registry cleanup independently of archive location, with idempotent retry on each delivery path. Expose registry activity and stale entries in `specle changes`, and install the registry ignore rule in new projects. Define the preparation-only handoff so it returns to activation without executing tasks, and update the public lifecycle reference to match the implemented abbreviated and S-sized workflows.

Specify appropriate behaviour for all supported kinds from existing workflow ownership; unsupported kinds or states must produce a clear diagnostic rather than being treated as normal changes. This definition is independent of `refactor-change-record`, `consolidate-state-enums`, and the current listing change. It does not activate this change or introduce dependencies on future work.

Verify kind- and state-specific dispatch, preparation and named build, preservation of selection, relationship boundaries, selected and unselected spike behaviour, next-action reporting, unsupported cases, and the existing normal workflow, alongside project quality gates.
